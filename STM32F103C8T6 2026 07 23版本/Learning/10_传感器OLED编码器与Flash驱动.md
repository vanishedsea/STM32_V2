# 第 10 章：传感器、OLED、编码器与 Flash 驱动拆解

本章不把驱动看成一组“能跑的函数”，而把它拆成边界、状态、数据转换、错误传播和资源成本。阅读时请同时打开裸机版 `App/Inc` 与 `App/Src` 中对应文件。

## 10.1 驱动的五层职责

一个可维护的设备驱动通常包含：

1. **传输层**：I2C/SPI 收发、CS 控制、超时；
2. **协议层**：命令、寄存器、字节序、CRC；
3. **器件层**：初始化、ID 检查、校准、忙状态；
4. **服务层**：组合多个器件、缓存、调度、重试；
5. **业务层**：UI、日志、报警等功能。

本项目的 `sht30.c`、`bmp280.c` 等属于器件驱动，`sensor_service.c` 属于服务层，`ui_service.c` 和 `storage_service.c` 消费整理后的数据。

## 10.2 先读头文件：驱动合同

以 `sensor_service.h` 为例：

```c
uint8_t sensor_service_init(I2C_HandleTypeDef *i2c);
uint8_t sensor_service_read(app_snapshot_t *snapshot, uint32_t sequence);
```

从两行声明就应追问：

- `i2c` 能否为 `NULL`？谁拥有它？生命周期多长？
- 返回的 `uint8_t` 是布尔值、错误码还是位掩码？
- `snapshot` 是输入、输出还是输入输出？
- 失败时输出对象会保持旧值、部分更新，还是整体重建？
- 函数会阻塞多久？是否线程安全？

当前实现每次先在局部变量 `next` 中构造完整快照，最后整体赋值给调用者。这样调用者不会在读取中途看到半新半旧的数据。

## 10.3 统一快照与有效位

`app_snapshot_t` 汇集时间、温湿度、气压和光照。它还有 `sequence` 与 `valid_mask`。

有效位的优势是：

- 某个传感器失败不必让整个系统失败；
- UI 可对无效值显示 `--`；
- 日志保留“采样时哪些字段可信”；
- 不需要用 `0.0`、`-1.0` 等可能与真实值冲突的魔法值。

典型判断：

```c
if ((snapshot->valid_mask & APP_VALID_SHT30) != 0U) {
    /* 温湿度有效 */
}
```

位掩码是“多个独立布尔状态打包到一个整数”的数据结构，不应与枚举序号混淆。

## 10.4 DS3231：BCD、时间与掉电状态

DS3231 的日期时间寄存器使用 BCD（Binary-Coded Decimal）。十进制 45 不保存为二进制 `0x2D`，而保存为 `0x45`：高半字节 4，低半字节 5。

```c
static uint8_t bcd_to_binary(uint8_t bcd)
{
    return (uint8_t)(((bcd >> 4) * 10U) + (bcd & 0x0FU));
}

static uint8_t binary_to_bcd(uint8_t value)
{
    return (uint8_t)(((value / 10U) << 4) | (value % 10U));
}
```

驱动还需要处理：

- 12/24 小时制位；
- 世纪位与年份范围；
- 日期合法性；
- oscillator stop flag，判断备用电源期间是否失去计时；
- 多字节读取期间秒进位带来的一致性问题。

当前 `sensor_service_init()` 检查掉电/振荡停止标志，必要时用固件构建时间设置时钟。这里的设计思想是“发现数据不可信时建立一个明确基线”，而不是默默显示随机时间。

## 10.5 SHT30：命令、等待、CRC 与物理量

SHT30 常见测量过程：

1. 发送单次测量命令；
2. 等待内部转换；
3. 读取温度原始值、温度 CRC、湿度原始值、湿度 CRC；
4. 验证 CRC；
5. 按数据手册公式换算。

典型换算关系为：

```text
T = -45 + 175 × raw_T / 65535
RH = 100 × raw_RH / 65535
```

驱动应先用整数拼出 16 位原始值：

```c
uint16_t raw = (uint16_t)(((uint16_t)rx[0] << 8) | rx[1]);
```

注意先把 `rx[0]` 转成足够宽的无符号类型再左移，可避免整型提升和符号问题。

### 10.5.1 CRC 的作用边界

CRC 能发现传输或存储中的许多位错误，但它不是加密，也不能证明传感器物理测量一定正确。供电噪声、热源影响或传感器安装不当可能产生“协议上完全正确、物理上却偏差”的数据。

## 10.6 BMP280：校准系数与补偿算法

BMP280 的原始温度/压力不能直接按简单比例解释。初始化时要：

1. 读取并验证 chip ID；
2. 读取芯片内部出厂校准系数；
3. 配置过采样、滤波和工作模式；
4. 读取 ADC 原始值；
5. 先补偿温度得到中间量 `t_fine`；
6. 再使用 `t_fine` 补偿压力。

这说明驱动对象有持续状态：校准参数不是每次读取都应重新获取。它们适合保存在文件内 `static` 结构中，或未来封装为 C++ 对象成员。

补偿公式的风险包括：

- 有符号/无符号混用；
- 中间乘法溢出；
- 错误字节序；
- 把 20 位原始值当 16 位；
- 改写厂商公式时运算顺序变化；
- 浮点版本与定点版本误差不同。

不要仅凭“结果看起来像气压”判断正确，应与已知库、当地海平面气压趋势或另一设备交叉验证。

## 10.7 BH1750：简单设备也有状态

BH1750 相对简单，但仍要处理：

- 地址脚决定 `0x23` 或 `0x5C`；
- 上电/复位/测量模式命令；
- 不同分辨率模式的转换时间；
- 两字节大端原始值；
- 模式对应的换算系数。

如果发送测量命令后立即读取，读到旧值或无效值并不代表 I2C 传输层坏了；可能只是器件状态机尚未完成转换。

## 10.8 传感器服务：部分失败与快照提交

当前 `sensor_service.c` 的关键模式是：

```c
app_snapshot_t next;
memset(&next, 0, sizeof(next));
next.sequence = sequence;

/* 每个设备单独尝试，成功才设置对应有效位 */

*snapshot = next;
```

这叫“先构造，后提交”。它降低了共享数据出现撕裂状态的概率。FreeRTOS 版本还应在任务间通过队列传递快照值，避免 UI 在传感器任务修改同一对象时同时读取。

可以进一步讨论三种失败策略：

| 策略 | UI 结果 | 优点 | 风险 |
|---|---|---|---|
| 失败即无效 | 显示 `--` | 诚实、明确 | 短暂抖动影响体验 |
| 保留上次值并标陈旧 | 继续显示并带 stale 标志 | 画面稳定 | 必须显示数据年龄 |
| 自动重试 | 可能恢复 | 用户无感 | 重试过密会占总线、拖慢系统 |

未来可给快照增加 `sample_tick` 或每个字段的年龄，从“有/无效”进化到“有效但陈旧”。

## 10.9 SSD1306 显存模型

128×64 单色屏共有 8192 个像素，即 1024 字节。SSD1306 常按 8 个 page 组织，每个 page 高 8 像素、宽 128 列。

像素 `(x, y)` 的典型映射：

```c
uint16_t index = (uint16_t)(y / 8U) * 128U + x;
uint8_t mask = (uint8_t)(1U << (y & 7U));
```

设置像素：

```c
buffer[index] |= mask;
```

清除像素：

```c
buffer[index] &= (uint8_t)~mask;
```

一个字节并不是水平方向连续 8 个像素，而是同一列一个 page 内的垂直 8 个像素。这是初学绘图最容易弄反的地方。

## 10.10 双缓冲比较与局部更新

当前优化裸机版 `ssd1306.c` 使用：

```c
static uint8_t s_buffer[1024];
static uint8_t s_sent_buffer[1024];
```

`s_buffer` 是希望显示的新画面，`s_sent_buffer` 是已成功发送画面的镜像。刷新时：

1. 对每个 page 先 `memcmp` 128 字节；
2. 完全相同则跳过；
3. 不同则从两端寻找首尾变化列；
4. 只发送变化列；
5. 发送成功后复制到 `s_sent_buffer`。

### 10.10.1 用 SRAM 换 I2C 带宽

代价是多用 1024 字节 SRAM，收益是在菜单只改变一个方框或几个字符时显著减少 I2C 发送。

全屏 I2C 原始数据量约 1024 字节。忽略起止与命令开销，400 kbit/s 下仅数据位时间下限约为：

```text
1024 × 9 / 400000 ≈ 23.0 ms
```

每字节还包括 ACK 的第 9 位，并且有命令、地址和软件开销。因此若每 20 ms 强制全刷，理论上总线几乎持续繁忙。局部刷新对响应和功耗非常重要。

### 10.10.2 这是不是极致方案

不是。仍可选择：

- 每 page 维护脏列范围，绘制时直接标记，避免每帧 `memcmp`；
- 只保留 dirty bitmap，减少第二缓冲区 SRAM；
- 用状态机或 DMA 异步发送；
- 合并多个脏矩形；
- 缓存文本布局，数据不变时不重新格式化；
- 使用 SPI OLED 提高链路带宽。

但每种方案都会增加代码和状态复杂度。当前双缓冲差异检测是“易理解、稳定、收益明显”的合理折中。

## 10.11 字体和反色动画

Nokia 风格菜单的核心不是图片资源，而是：

- 四个矩形布局；
- 文本与边框绘制；
- `invert_rect()` 对选中区域做 XOR；
- 编码器改变目标格；
- 6 帧过渡动画逐步改变高亮区域。

XOR 的性质：

```text
bit XOR 1 = 取反
bit XOR 0 = 不变
同一区域 XOR 两次 = 恢复原状
```

这也是位运算在图形中的直接应用。动画是否“丝滑”不只取决于帧数，还受 I2C 刷新时间、调度抖动、绘制范围和输入事件处理影响。

## 10.12 W25Q64：地址空间和物理约束

W25Q64 容量为 64 Mbit，即 8 MiB。常见组织：

- 256 字节 page；
- 4 KiB sector；
- 更大的 32/64 KiB block；
- 整片擦除。

项目当前划分：

- 设置从地址 0 开始，使用设置扇区；
- 日志区域从 `0x10000` 开始；
- 日志区域大小 64 KiB；
- 每条日志记录固定 32 字节。

理论记录槽数量：

```text
64 KiB / 32 B = 2048 条
```

若每 60 秒记录一次：

```text
2048 分钟 ≈ 34.13 小时
```

这说明当前区域只是教学/短期数据记录。若需要数周历史，应扩大区域、降低采样频率、压缩记录或设计导出机制。

## 10.13 日志记录的数据建模

当前 `log_record_t` 被显式压缩为 32 字节，并用编译期断言验证大小：

```c
typedef char log_record_size_must_be_32[
    (sizeof(log_record_t) == 32U) ? 1 : -1
];
```

记录包含：

- magic；
- sequence；
- 日期时间；
- valid mask；
- 百分之一单位的温度、湿度、光照；
- Pa 整数气压；
- CRC32。

把浮点量转换为定点整数有三点收益：

1. 文件格式长度固定；
2. 不依赖编译器浮点表示细节来解释日志；
3. 节约空间并便于比较。

同时必须明确比例和范围，例如 `temperature_centi = 2534` 表示 25.34 °C。

## 10.14 CRC、Magic、Version 和 Sequence

- **Magic**：快速判断一个区域是否像本格式记录；
- **Version**：支持未来格式升级；
- **CRC32**：发现内容损坏或未完整写入；
- **Sequence**：判断新旧和环形覆盖后的最近记录；
- **Valid mask**：描述字段级可信度。

这几项组合形成最小的持久化协议。仅保存裸结构体而没有这些元数据，掉电、版本变化和随机数据都很难处理。

序列号比较同样需要考虑回绕：

```c
static bool sequence_is_newer(uint32_t a, uint32_t b)
{
    return (int32_t)(a - b) > 0;
}
```

## 10.15 非阻塞存储状态机

当前裸机 `storage_service_process(now_ms)` 将擦除/编程分为：

```text
IDLE → 启动擦除 → WAIT_ERASE → 启动编程 → WAIT_PROGRAM → 校验 → IDLE
```

每 5 ms 被调度一次。等待阶段只查询 WIP 状态，不在一个函数里死等 3 秒。这样：

- 编码器仍能响应；
- OLED 动画仍可推进；
- 蜂鸣器能按时关闭；
- 看门狗未来可以正常喂；
- 超时路径明确。

注意“非阻塞”不是完全不花时间：每次 SPI 查询和最终校验仍消耗时间，只是把长等待分散到多轮主循环。

## 10.16 设置磨损与日志磨损

设置采用多个 slot 追加，写满扇区后再擦除，而不是每次切换主题都擦整扇区。这是一种简化的日志结构存储，可降低擦写次数。

仍可继续改进：

- 设置变更后延迟数秒再保存，合并连续旋转/切换；
- 只有内容变化才写；
- 为每个扇区统计擦除次数；
- 双扇区交替，提升掉电安全；
- 两阶段提交或有效标记最后写入；
- 对关键设置提供默认值和版本迁移。

## 10.17 蜂鸣器：输出也需要状态机

有源蜂鸣器只需要开/关，但不能在业务代码中写：

```c
buzzer_on();
HAL_Delay(1000);
buzzer_off();
```

这会冻结整个系统。正确模型是记录关闭截止时间：

```c
void buzzer_beep(uint32_t now, uint32_t duration)
{
    buzzer_set(true);
    off_deadline = now + duration;
    active = true;
}

void buzzer_process(uint32_t now)
{
    if (active && (int32_t)(now - off_deadline) >= 0) {
        buzzer_set(false);
        active = false;
    }
}
```

项目启动提示约 40 ms，错误提示约 100 ms；并通过设置允许关闭按键蜂鸣反馈。蜂鸣器有效电平配置必须与实际三脚模块匹配。

## 10.18 驱动测试策略

按从小到大的顺序：

1. 设备存在性：I2C ACK / JEDEC ID / chip ID；
2. 原始字节：打印或观察寄存器值；
3. CRC/校准：注入已知数据做纯函数测试；
4. 单设备物理量：与参考仪表对照；
5. 多设备共享总线：连续运行、统计错误；
6. 服务层快照：拔掉单个设备时其他设备仍工作；
7. UI/日志：有效位、显示和持久化一致；
8. 故障恢复：总线卡住、Flash 忙超时、掉电重启。

换算公式、CRC、环形地址等纯算法可以在 PC 上用普通 C 测试，不必每次下载到板上。

## 10.19 本章练习

1. 为 `app_snapshot_t` 增加 `sample_tick_ms`，UI 显示数据年龄；不要破坏现有日志格式。
2. 计算日志间隔改为 10 秒、5 分钟时，64 KiB 分别能保存多久。
3. 设计一个 `sensor_status_t`，分别记录 absent、ok、crc_error、timeout、stale。
4. 解释为什么 OLED 使用第二个 1024 字节缓冲区可能反而提升系统整体响应。
5. 给 W25Q64 写入路径画出超时、校验失败和重试状态图。
6. 比较“立即把设置写 Flash”和“停止操作 3 秒后再写”的磨损与掉电风险。
