# 第 8 章：STM32F103 与 Cortex-M3——从 C 代码到真实硬件

本章开始把前面的 C 语言知识放回芯片。你会看到：变量、指针和位运算并不是抽象语法，它们最终会变成对寄存器、内存和外设的真实操作。

## 8.1 本章目标

学完后应能解释：

1. STM32F103C8T6、Cortex-M3、CMSIS、HAL 分别是什么；
2. Flash、SRAM、外设寄存器位于怎样的地址空间；
3. 上电后为什么先执行 `Reset_Handler`，而不是直接进入 `main()`；
4. 时钟、复位、总线和 GPIO 为什么互相关联；
5. 中断发生时 CPU 自动保存了什么；
6. `volatile` 为什么常用于寄存器和中断共享变量，但不能替代同步机制；
7. HAL 帮我们做了什么，以及如何逐层下探到寄存器。

## 8.2 三个名字代表三个层次

| 名称 | 含义 | 在本项目中的位置 |
|---|---|---|
| ARM Cortex-M3 | CPU 内核架构 | 指令集、寄存器、异常模型、NVIC、SysTick |
| STM32F103C8T6 | ST 在 Cortex-M3 周围加入 Flash、SRAM、GPIO、I2C、SPI 等形成的 MCU | 实际蓝色小板上的主芯片 |
| STM32 HAL/CMSIS | 帮助 C 代码访问内核和芯片外设的软件层 | `Drivers/`、`Core/` 中的头文件与源码 |

可以把它想成：Cortex-M3 是发动机设计，STM32F103 是整辆车，CMSIS/HAL 是驾驶控制接口。

## 8.3 存储器映射：地址不只代表 RAM

Cortex-M3 使用统一的 32 位地址空间。CPU 读写某个地址时，芯片内部的地址译码电路决定访问 Flash、SRAM 还是外设。

典型 STM32F103 地址区域如下：

| 区域 | 常见起始地址 | 用途 |
|---|---:|---|
| Flash | `0x08000000` | 程序机器码、只读常量、初始值镜像 |
| SRAM | `0x20000000` | 全局变量、栈、运行时数据 |
| 外设 | `0x40000000` | GPIO、I2C、SPI、定时器等寄存器 |
| Cortex 内核外设 | `0xE0000000` 附近 | NVIC、SysTick、调试组件 |

“寄存器”在 C 中通常被描述为某个固定地址上的 `volatile` 对象。例如下面是原理演示，不建议直接替换项目 HAL 代码：

```c
#define PERIPH_BASE       0x40000000UL
#define APB2PERIPH_BASE   (PERIPH_BASE + 0x00010000UL)
#define GPIOC_BASE        (APB2PERIPH_BASE + 0x00001000UL)
#define GPIOC_ODR         (*(volatile uint32_t *)(GPIOC_BASE + 0x0CUL))

/* 修改 PC13 输出数据位。真实项目还必须先打开 GPIOC 时钟并配置模式。 */
GPIOC_ODR &= ~(1UL << 13);
```

这段代码同时用到了：

- 整数常量和十六进制；
- 指针强制转换；
- 指针解引用；
- `volatile`；
- 位运算。

因此，前七章不是“学完才开始单片机”，而是在学习单片机代码最基本的表达工具。

## 8.4 Flash、SRAM、栈和堆

典型程序段可以这样理解：

| 段 | 主要内容 | 上电后的所在地 |
|---|---|---|
| `.text` | 函数机器码 | Flash |
| `.rodata` | 字符串、`const` 常量 | 通常在 Flash |
| `.data` | 有非零初值的全局/静态变量 | 初值在 Flash，运行对象在 SRAM |
| `.bss` | 零初始化的全局/静态变量 | SRAM，启动时清零 |
| stack | 局部变量、返回地址、保存的寄存器 | SRAM，通常向低地址增长 |
| heap | 动态分配区域 | SRAM；本项目核心路径不依赖动态分配 |

STM32F103C8T6 的 SRAM 很有限，所以 OLED 全屏缓冲区、任务栈、队列和大数组都必须计算。一个 128×64 单色 OLED 全帧缓冲区需要：

```text
128 × 64 ÷ 8 = 1024 字节
```

这只是像素数据，还不包括 UI 状态、传感器快照、通信缓冲区和栈。

### 8.4.1 为什么不建议在主控制路径随意 `malloc`

动态分配并非语法错误，但在长期运行的 MCU 中会带来：

- 分配失败路径；
- 碎片；
- 执行时间不稳定；
- 所有权和释放时机难以证明；
- 内存越界更难定位。

本项目更适合静态数组、固定容量队列和静态任务栈。FreeRTOS 版本也明确启用了静态分配，关闭动态分配。

## 8.5 复位后发生了什么

执行链大致为：

```mermaid
flowchart LR
    A["上电或复位"] --> B["从向量表取初始 MSP"]
    B --> C["进入 Reset_Handler"]
    C --> D["复制 .data 到 SRAM"]
    D --> E["清零 .bss"]
    E --> F["SystemInit 配置基础时钟"]
    F --> G["C 运行库初始化"]
    G --> H["调用 main"]
```

项目中的启动文件位于 `Core/Startup/arm/`。启动文件除了 `Reset_Handler`，还包含中断向量表。向量表本质上是函数地址数组：第一个元素特殊地保存初始主栈指针，其后保存复位和各异常/中断处理函数地址。

这解释了两个现象：

1. `main()` 不是芯片执行的第一条用户相关代码；
2. 中断函数名字必须与启动文件和库约定一致，否则可能进入默认处理函数并看起来“锁死”。

## 8.6 Cortex-M3 的核心寄存器

不必一开始背完，但要知道它们的职责：

| 寄存器 | 作用 |
|---|---|
| R0–R3 | 参数、临时值、返回值 |
| R4–R11 | 通用寄存器，函数调用时按 ABI 规则保存 |
| R12 | 临时寄存器 |
| R13 / SP | 栈指针；Cortex-M3 有 MSP 与 PSP |
| R14 / LR | 链接寄存器，通常保存返回信息 |
| R15 / PC | 程序计数器，指出下一条指令 |
| xPSR | 条件标志、执行状态、异常号 |

裸机主程序通常使用 MSP。FreeRTOS 调度后，任务一般在 PSP 上运行，异常处理使用 MSP。上下文切换的关键，就是保存当前任务还需要的寄存器，再恢复另一个任务的寄存器和栈指针。

## 8.7 时钟树：外设为什么必须“开时钟”

CPU 和外设由时钟边沿推进状态。RCC（Reset and Clock Control）负责选择时钟源、倍频、分频以及给外设门控时钟。

你的项目通常把系统时钟配置到 72 MHz，并让 APB1、APB2 等总线得到合适频率。要特别注意：

- GPIO、AFIO、I2C、SPI 等使用前必须使能对应时钟；
- APB1 外设通常有较低最高频率限制；
- 定时器时钟在某些 APB 分频条件下会自动乘 2；
- I2C 的 400 kHz 是总线 SCL 频率，不等于 CPU 频率；
- 改动系统时钟会影响 `HAL_Delay`、串口波特率、I2C/SPI 和 FreeRTOS tick。

调试“外设完全不工作”时，时钟使能和 GPIO 复用配置应排在很前面检查。

## 8.8 总线：AHB、APB1、APB2

外设挂在不同内部总线上：

- AHB：连接 CPU、存储器、DMA 等高速资源；
- APB1：I2C、SPI2、部分定时器等；
- APB2：GPIO、AFIO、SPI1、部分定时器等。

当 C 代码写 `GPIOB->ODR` 时，CPU 发起一次总线写事务，地址译码把它送到 GPIOB。HAL 函数最终也必须完成类似的寄存器访问，只是额外提供参数检查、状态管理和跨型号统一接口。

## 8.9 NVIC 与中断

NVIC 是 Cortex-M3 的嵌套向量中断控制器。它负责：

- 使能或禁止某个中断；
- 设置优先级；
- 记录 pending 状态；
- 在更高优先级到来时嵌套；
- 根据向量表跳转到处理函数。

进入异常时，硬件自动把 R0–R3、R12、LR、PC、xPSR 等压入当前栈。处理函数返回时硬件恢复它们。这使普通 C 中断函数成为可能。

### 8.9.1 中断处理函数应该短

本项目裸机版的 EC11 优化思路是：

1. PB12/PB13 边沿触发 EXTI；
2. 中断里只采样、更新很小的解码状态或累计量；
3. 2 ms 调度任务取走结果；
4. UI 和 OLED 刷新留在普通任务上下文。

不要在编码器中断里直接刷新 OLED、访问慢速 I2C、擦除 Flash 或长时间延时。否则会增加中断延迟，甚至阻塞其他时间敏感工作。

## 8.10 SysTick 与毫秒时间基准

SysTick 是 Cortex-M3 自带的 24 位递减计数器。HAL 常用它产生 1 ms 时间基准，维护 `HAL_GetTick()` 返回值。裸机调度器根据毫秒 tick 判断任务是否到期。

正确的超时比较应考虑 32 位计数回绕。本项目采用类似：

```c
if ((int32_t)(now - deadline) >= 0) {
    /* deadline 已到 */
}
```

不要写：

```c
if (now >= deadline) { /* 回绕附近可能出错 */ }
```

前一种写法假设任意一次计划间隔小于有符号 32 位范围，即不到约 24.8 天；这对毫秒级周期任务成立。

## 8.11 HAL、LL、CMSIS 和寄存器的层次

| 层次 | 优点 | 代价/风险 | 适合场景 |
|---|---|---|---|
| HAL | 可读、统一、初始化方便 | 调用层次较多、部分接口阻塞 | 大多数业务与驱动初始化 |
| LL | 更接近寄存器、开销低 | 型号相关性更高 | 时间敏感又希望保留库表达 |
| CMSIS/设备头文件 | 寄存器结构和内核接口标准化 | 需要懂硬件细节 | 中断、内核、精确控制 |
| 裸寄存器 | 控制最直接 | 可移植性、可维护性较差 | 学习或少数极限热点 |

优化不能简单等同于“把 HAL 全删掉”。更合理的方法是：

1. 先测量瓶颈；
2. 保留 HAL 做正确且不敏感的初始化；
3. 对 OLED 刷新、编码器输入等明确热点采用局部优化；
4. 保持同一外设的状态管理一致，避免 HAL 与直接寄存器操作互相破坏。

## 8.12 在项目中追踪一次 GPIO 写操作

以蜂鸣器为例，建议按以下顺序阅读：

1. `App/Inc/buzzer.h`：模块公开接口；
2. `App/Src/buzzer.c`：有源电平和定时关闭逻辑；
3. `App/Inc/app_config.h`：蜂鸣器有效电平、启动提示时长；
4. `Core/Src/main.c`：GPIO 初始化和周期服务调用；
5. HAL GPIO 源码：最终如何读写 BSRR/BRR/ODR。

这种“从业务 API 向下追到寄存器”的阅读路径，比从参考手册第一页开始硬背更容易建立完整模型。

## 8.13 实验：观察内存与启动过程

### 实验 A：查看 Keil Map 文件

1. 在 Keil Target 设置中启用生成 Map；
2. Build 后打开输出目录中的 `.map`；
3. 找到 `.text`、`.data`、`.bss`、ZI Data、RW Data；
4. 找到 `main`、OLED 缓冲区、任务栈或事件队列；
5. 记录它们的地址和大小。

思考：为什么零初始化的大数组会增加 SRAM 使用，却不需要在 Flash 中逐字节保存零？

### 实验 B：在调试器中观察复位

先确保 ST-Link 能稳定连接，并使用“Reset and Run”或在 `main` 断点。不要在下载后自动启动一个无目标连接的调试会话。若调试连接不稳定，先参考根目录 `04_ST-Link故障排查.md`。

观察：

- PC 是否进入 `Reset_Handler`；
- SP 初始值是否位于 `0x2000....` SRAM；
- 何时到达 `main`；
- 全局零初始化变量进入 `main` 时是否已为 0。
