# 第 17 章：调试、性能优化与可靠性

优化不是“看到 HAL 就删”，调试也不是“多烧录几次”。可靠的工程方法是：先分类、再测量、建立假设、做最小改动、验证结果、保留回退基线。

## 17.1 故障分类树

### A. 构建失败

- 编译错误；
- 链接错误；
- Flash/RAM region overflow；
- Pack/头文件/路径配置错误。

### B. 下载失败

- ST-Link 未识别；
- SWDIO/SWCLK/GND/Vref 接线；
- 目标板没供电；
- Reset/连接模式；
- Flash algorithm 或设备选择；
- 固件把 SWD 引脚/低功耗状态配置不当；
- 克隆下载器驱动/固件问题。

### C. 下载成功、调试连接失败

Keil 输出若先出现：

```text
Erase Done.
Programming Done.
Verify OK.
Flash Load finished
```

随后才出现 `No target connected` 或 `Target DLL has been cancelled`，通常是下载已完成，Keil 随后自动启动调试会话时失去连接。应调整“下载后是否自动进入 Debug”、复位与连接方式，而不是把成功下载误判为编译失败。

### D. 能运行但功能错误

- 引脚/地址/有效电平错误；
- 传感器状态或换算；
- UI 状态机；
- 队列丢事件；
- 数据无效位；
- Flash 格式/版本。

### E. 随机锁死/复位

- 栈溢出；
- HardFault/BusFault；
- 看门狗或棕断复位；
- ISR/FreeRTOS 优先级错误；
- 无限等待；
- 数据竞争/内存越界；
- 供电/地弹/上拉/EMI。

先确定属于哪一类，能省掉大量无效修改。

## 17.2 可观测性设计

系统至少应能回答：

- 上次为什么复位？
- 初始化到哪一步？
- 每个 I2C 设备是否存在？
- 最近一次错误类型、设备和时间？
- 事件/RTOS 队列是否丢失？
- 任务最大执行时间/栈高水位？
- Flash 是否 ready、日志数量、最近写入结果？
- UI 当前 page/theme/selection？

可观测手段：

- UART 低频结构化日志；
- PC13 心跳/错误闪码；
- OLED 诊断页；
- GPIO 测时脉冲；
- fault record；
- 计数器和高水位；
- SWD 断点/Watch/Memory/Call Stack；
- 逻辑分析仪和示波器。

日志本身有时序与栈成本。中断内不要格式化长字符串；高频路径只增加计数或写固定记录，低频任务再输出。

## 17.3 一次科学调试循环

1. **复现**：写出操作、接线、固件版本、发生概率；
2. **分类**：构建/下载/启动/运行/硬件；
3. **证据**：输出、复位标志、fault PC、波形、计数器；
4. **假设**：必须能被实验证伪；
5. **最小实验**：一次只改变一个关键变量；
6. **结果**：支持或反驳假设；
7. **修复**：处理根因和错误路径；
8. **回归**：正常、边界、长时间、拔设备、快速输入；
9. **记录**：避免下次重复调查。

不要同时改时钟、引脚、HAL 版本、任务优先级和 UI，然后用“好像不锁了”作为结论。

## 17.4 性能指标不是只有 CPU 频率

本项目至少关注：

- 输入到视觉反馈的延迟；
- UI 帧时间和抖动；
- I2C 总线占用；
- 传感器采样完成时间；
- Flash 擦写期间的最坏响应；
- CPU 活跃率/空闲率；
- Flash 代码体积；
- SRAM 静态占用；
- 裸机最大栈/RTOS 各任务栈；
- 功耗；
- 丢事件/丢日志；
- 复位恢复时间。

一种优化常在另一个维度付费，例如第二 OLED 缓冲增加 1024 B SRAM，却减少大量 I2C 传输并提升 UI 响应。

## 17.5 优化顺序

推荐按收益/风险：

1. 删除无用工作；
2. 降低工作频率；
3. 只处理变化数据；
4. 把长等待改为阻塞任务/状态机；
5. 改善算法和数据布局；
6. 合并通信事务；
7. 使用中断/DMA；
8. 局部减少抽象/直接寄存器；
9. 汇编级微优化。

当前 UI 的 dirty + changed-column 刷新属于前几项，通常比把一个小循环手写汇编收益大得多。

## 17.6 当前裸机版优化状态

| 领域 | 当前做法 | 评价 | 下一步 |
|---|---|---|---|
| 调度器 | 8 槽固定数组 O(N) | 当前规模已很合适 | 加统计，不必换复杂结构 |
| 时间比较 | 有符号差值处理回绕 | 正确且常用 | 保持间隔小于半范围 |
| 事件总线 | 16 项固定环形队列 + dropped | 清晰、确定 | 高水位、事件合并、并发边界 |
| UI 业务 | dirty 才刷新 | 高收益 | 细分 dirty 仅在确有需要时 |
| OLED 驱动 | 当前/已发送双缓冲，按 page 与变化列发送 | 显著优化总线 | dirty ranges、异步/DMA 需实测权衡 |
| 编码器 | EXTI 捕获 + 2 ms 消费 | 响应/空闲开销好 | 抖动统计、累计合并 |
| Flash | 擦写状态机，5 ms 推进，超时与校验 | 避免秒级主循环阻塞 | 掉电事务、磨损统计、增量启动扫描 |
| 内存 | 固定数组，无核心动态分配 | 可预测 | map/栈实测后再收缩 |
| 空闲 | `WFI` | 避免忙等 | tickless 不是当前优先项 |
| 蜂鸣器 | 短启动/错误阻塞，正常不常响 | 风险较低但不统一 | 改为统一非阻塞 pulse 状态机 |

已经“接近极致”的是：小任务数的线性调度和固定队列结构本身。仍有明显空间的是驱动阻塞、故障统计、恢复、掉电一致性和实测闭环。

## 17.7 当前 FreeRTOS 版优化状态

| 领域 | 当前做法 | 评价 | 下一步 |
|---|---|---|---|
| 内存分配 | 全静态任务/队列/mutex | 很适合固定系统 | 依据高水位缩栈 |
| 周期任务 | `vTaskDelayUntil` | 减少漂移 | 统计超期 |
| UI 快照 | 长度 1 overwrite queue | 语义正确 | 保持 |
| 输入 | 长度 8 event queue | 简单 | 统计满/合并旋转 |
| I2C | mutex | 必要 | 测持锁时间、统一所有访问 |
| 编码器 | 2 ms 高优先级轮询 | 能用但固定唤醒 | 可移植裸机 EXTI + notification |
| Flash | storage 任务同步等待 | 不冻结高优先级任务，但会耗 CPU/影响低优先级 | delay/通知/状态机 |
| 共享状态 | `volatile bool` flash ready | 仅最低限度可见性 | 队列/通知/单一所有者 |
| 栈 | 约 6 KiB 显式栈 | 余量未知 | 高水位 + map |
| tickless | 关闭 | 对当前教学合理 | 功耗目标明确后再做 |

比较两版性能前先同步 OLED/Flash/编码器驱动策略，否则不是纯调度模型比较。

## 17.8 OLED 性能进一步分析

### 17.8.1 渲染成本与传输成本分开测

- 渲染：clear、draw text、invert、布局；
- diff：memcmp、找首尾变化；
- I2C：命令 + 数据发送；
- HAL/中断：驱动开销。

若 I2C 占 95%，优化字体循环意义有限；若动画只改小区域但每次重新格式化所有浮点，渲染可能成为可见成本。

### 17.8.2 脏矩形/脏列

当前双缓冲需要 2048 B，并每次比较最多 1024 B。替代方案：每个 page 维护 `dirty_min[8]` 和 `dirty_max[8]`：

```text
绘制像素时更新对应 page 的最小/最大列
刷新时仅发送范围
成功后重置 dirty
```

收益：可删除 sent buffer，节省约 1024 B，也省全页比较。

风险：

- 所有绘图函数都必须正确标脏；
- `clear()`、invert、文本缩放边界更容易遗漏；
- I2C 失败后 dirty 不能错误清除；
- 同一 page 两个相距很远的小区会发送中间未变化列。

是否替换应先确认 SRAM 是否真正紧张。若还有充足 RAM，当前方案更可靠。

### 17.8.3 缓存格式化文本

传感器每秒更新，UI 动画 20 ms。动画期间不必每帧重新把浮点转换为字符串。可在新快照事件时生成显示字符串，动画仅移动/反色。

进一步可不用 `snprintf("%.2f")`，写受控定点格式化函数，减少代码体积和软件浮点格式化成本。但要处理负数、舍入、范围和 `--`。

## 17.9 传感器性能与总线调度

传感器 1 秒采样，不需要盲目追求微秒。但单次批量读若阻塞 UI 数十毫秒，可：

- 把启动转换与读取结果拆开；
- 在多个 5/10 ms 阶段轮转设备；
- 将快速 RTC 读取与慢转换分开；
- 缓存 BMP280 校准参数；
- 失败设备降低重试频率，例如指数退避；
- 统计每个地址 NACK/CRC/timeout；
- I2C 恢复后重新 init 设备。

不要每秒重新扫描全 I2C 地址空间。扫描适合启动/诊断；正常运行应访问已知设备。

## 17.10 Flash 性能、寿命与一致性

### 17.10.1 吞吐不是主要限制

每分钟仅写 32 B，平均数据率极低。真正问题：

- 扇区擦除可达数百毫秒甚至更久；
- 掉电可能打断擦写；
- 扇区有限擦除寿命；
- 启动扫描时间随区域增大；
- 设置频繁变化可能集中磨损。

### 17.10.2 掉电安全方案

可设计记录两阶段：

1. 擦除态全 `0xFF`；
2. 写 payload + CRC，但 valid marker 留 `0xFF`；
3. 校验 payload；
4. 最后把 valid marker 某位从 1 写 0，提交记录。

由于 NOR Flash 编程能 1→0，最后小写可作为提交点。启动只承认 marker 与 CRC 都正确的记录。

对设置可用 A/B 两扇区、generation 和 commit marker。擦旧扇区前确保新副本已完整提交。

## 17.11 SRAM 优化

按优先级查：

1. 大静态数组/任务栈；
2. 同一数据是否多份缓存；
3. 大局部数组是否推高栈；
4. 字体/const 表是否误放 SRAM；
5. 结构体 padding；
6. 队列是否复制过大对象；
7. debug 缓冲和日志格式；
8. C++ vptr/RTOS TCB 等对象成本。

### 17.11.1 不要用 packed 解决所有 RAM

`packed` 会降低对齐、可能生成更多指令或产生非对齐风险。只对持久化/协议记录在明确需要时使用。RAM 业务结构优先自然对齐并调整成员顺序：把同宽成员放一起可减少 padding。

### 17.11.2 Flash 换 RAM

只读字体表应 `const`，确保链接到 RO/Flash。字符串常量不要复制到大可写数组。C++ `constexpr` 表也应核对 map。

## 17.12 Flash 代码体积优化

常见大户：

- `printf` 浮点格式化；
- 通用除法/浮点辅助；
- 字体与图标；
- 未使用 HAL 模块；
- C++ iostream、异常、RTTI；
- 模板多实例；
- 重复 UI 绘制逻辑。

策略：

- 以 map 找大符号；
- 发布构建关闭无用调试文本或分级日志；
- 定点格式化替代通用 `%f`（经测试）；
- HAL 源文件只加入实际外设模块；
- 启用未使用 section 删除；
- 合并重复表/函数；
- 不要用晦涩微优化牺牲正确性换几十字节，除非确实接近边界。

## 17.13 看门狗设计

独立看门狗 IWDG 可在软件失控时复位，但错误用法是主循环无条件喂狗：即使传感器任务、UI 或存储已死，主循环某处仍可能继续喂。

健康喂狗模型：

1. 每个关键任务在完成一次有效周期后设置 heartbeat bit；
2. health task 检查所有必须位是否在窗口内出现；
3. 只有系统整体健康才喂 IWDG；
4. 清位开始下一窗口；
5. 可选任务故障不应阻止安全核心喂狗，但要降级/报告。

看门狗超时要大于正常最坏 Flash 擦除、启动扫描和调试暂停策略。开发时要有“连接 under reset”方案，避免错误固件让下载困难。

## 17.14 复位原因

RCC 状态寄存器可区分：

- 上电/掉电复位；
- NRST 外部复位；
- 软件复位；
- 独立/窗口看门狗；
- 低功耗复位等。

启动早期读取并记录，然后清标志。这样“它自己重启了”可以从猜测变成证据。

## 17.15 Fault record

HardFault 中避免复杂 HAL 和 Flash 擦写。可把固定小记录写入保留 RAM 区、备份寄存器或预先准备的安全位置：

```c
typedef struct {
    uint32_t magic;
    uint32_t stacked_pc;
    uint32_t stacked_lr;
    uint32_t cfsr;
    uint32_t hfsr;
    uint32_t bfar;
    uint32_t mmfar;
    uint32_t task_or_state;
    uint32_t crc;
} fault_record_t;
```

要求：

- 写入路径不依赖已损坏栈的大调用链；
- 不在 fault 中用普通 RTOS API/mutex；
- 记录区域启动时先验证 magic/CRC；
- 输出后清除或增加 generation；
- 不保存敏感信息；
- fault 后让执行器进入安全状态，再复位或停机。

## 17.16 断言分层

### 编译期

```c
_Static_assert(sizeof(log_record_t) == 32, "log record layout changed");
```

C++：

```cpp
static_assert(LogRegionSize % sizeof(LogRecord) == 0);
```

### 启动期

- I2C 地址不冲突；
- 任务/队列创建成功；
- JEDEC ID 正确；
- OLED 地址存在；
- 配置版本合法。

### 运行期

- 指针非空；
- 枚举范围；
- 队列不变量；
- Flash 地址/长度边界；
- ISR 优先级；
- 栈溢出 hook。

断言失败的处理必须关闭蜂鸣器/未来执行器，记录原因，再进入可诊断安全状态。

## 17.17 电源与硬件可靠性

软件锁死有时是电源问题：

- 多个模块去耦不足；
- I2C 上拉过强；
- W25Q64 写入电流造成压降；
- ST-Link 和目标板多路供电回灌；
- WS2812 未来接入时近 1 A 突变；
- 长杜邦线、地线阻抗和边沿振铃；
- NRST 悬空/干扰；
- 蜂鸣器模块驱动噪声。

诊断要用示波器看 3.3 V 和 NRST，不仅看万用表平均值。硬件接线和去耦说明见根目录 `01_硬件接线.md`。

## 17.18 长时间与故障注入测试

建议矩阵：

| 测试 | 观察 |
|---|---|
| 连续运行 24/72 小时 | 复位、I2C 错误、内存/栈、日志环绕 |
| 快速旋转 1 分钟 | 丢步、队列满、动画卡顿 |
| 反复按 PB15 | 消抖、短按/长按边界 |
| 拔掉单个 I2C 模块 | 超时、其他设备是否继续 |
| SDA 短暂拉低后释放 | 总线恢复能力 |
| Flash 写入时断电 | 记录/设置完整性 |
| 日志区域写满并环绕 | 最新 sequence 和擦除统计 |
| 主题连续切换 | 设置磨损/合并写入 |
| ST-Link 连接/断开 | 发布版是否依赖调试器 |
| 优化等级变化 | UB、时序和体积 |

故障注入必须在安全、低电压环境中进行，断电后改线。不要带电短接供电轨。

## 17.20 一步到位的优化路线图

### 第一层：现在即可做，风险低

- 加调度/队列/错误/栈统计；
- 蜂鸣器统一非阻塞；
- FreeRTOS 检查所有队列发送返回值；
- 记录复位原因；
- 低频 health 诊断；
- Map 基线表。

### 第二层：有测量后做

- 传感器分阶段；
- FreeRTOS Flash 状态机或延时轮询；
- OLED 格式化缓存/dirty range；
- 编码器事件累计；
- I2C 自动恢复与退避；
- 根据高水位缩 RTOS 栈。

### 第三层：可靠性升级

- IWDG 健康喂狗；
- fault record；
- Flash 双区/commit marker；
- 配置迁移；
- 自动硬件在环长测。

### 第四层：有明确需求才做

- OLED I2C DMA/异步队列；
- tickless idle；
- 无锁 ISR 队列；
- 局部 LL/寄存器重写；
- WS2812 TIM+DMA；
- 自定义 bootloader/固件升级。
